# Strategy Decomposition And Choice

Use this reference for a strategy, market, planning, or ambiguous decision that needs more depth than the main skill. It expands AY's canonical strategy loop. It does not add high-stakes evidence tables, research questionnaires, product page design, or long-running execution controls.

## Depth Boundary

Use only the stages that can change the decision or artifact, but check all six privately before omitting one. A framework with no causal priority or choice fails even when every heading is present. Deep reasoning does not authorize a deeper artifact tier: when AY asks to align on the framework first, compress the six stages into a decision map that shows the purpose, decisive research, decomposition logic, option or stage structure, and alignment choices. Do not write a section of developed prose for every stage; stop before filling the operating plan.

## 1. Purpose And Goal

Define:

- the decision or desired change;
- why it matters now;
- the person or system affected;
- the outcome and guardrails;
- the condition under which the work should not proceed.

Do not confuse activity, output, and outcome. A report, event, feature, or campaign is an artifact or mechanism, not automatically the goal.

## 2. Research Plan

Research only questions that can change the decision. For each decisive unknown, name the source or sample, acquisition action, expected artifact, and which option changes when the answer is known.

Load `research-question-design.md` when designing interviews, surveys, question trees, or a formal research plan. Do not expose research chronology in the final artifact unless the reader needs it to trust the conclusion.

## 3. Problem Decomposition And Priority

Build only the model needed to decide:

| Lens | Question |
| --- | --- |
| Situation | What are people doing now, what alternative are they using, and what pressure keeps the current state in place? |
| System | Which actors, incentives, value exchanges, dependencies, attention flows, resources, and constraints shape the result? |
| Cause | Which factors create the symptom, and which are only correlated or downstream? |
| Crux | Which one to three contradictions, bottlenecks, or unknowns determine the answer? |
| Priority | What must be solved first because other choices depend on it? |

Show dependencies or priority instead of presenting every issue as an equal pillar. Keep this decomposition private when exposing it would make the artifact heavier without improving judgment.

When the strategy operates across time, use phases to express those dependencies. A phase is a decision contract, not a calendar heading: it needs a relative time or timing trigger, entry condition, exit condition, core mechanism, decisive resource, owner or acquisition route, and observable indicator that supports the next decision. Mark unresolved values `待确认`; do not invent dates, people, budgets, or thresholds. Keep the phase map compact at framework depth; detailed tasks belong after alignment.

## 4. Options And Final Choice

Compare only viable mechanisms. For each, state:

- value and causal mechanism;
- required and missing resources;
- time, cost, and coordination load;
- reversible and irreversible commitments;
- risks and what the option deliberately gives up;
- evidence that would strengthen, weaken, or reverse it.

Recommend one route. If the choice must remain open, name the single uncertainty blocking it and the smallest resolving test. Do not end at “each has pros and cons.”

## 5. Execution

Translate the choice into the smallest useful next artifact, validation, or operating step.

| Field | Requirement |
| --- | --- |
| owner / acquisition | Real owner or role; otherwise `unassigned` plus how to acquire one |
| entry condition | What must be true before starting |
| action | The bounded work |
| artifact | What exists afterward |
| exit condition | What proves this step complete |
| failure signal | What triggers correction, pause, pivot, or stop |
| review point | When and with what input the next decision is made |

Do not invent precision to make a plan look executable. Unknown people, dates, budgets, thresholds, or permissions stay unknown and receive an acquisition or approval action.

Load `long-running-execution.md` only when the system itself must run over time, write durable state, coordinate consumers, pause, recover, or clean up.

## 6. Retrospective

A retrospective must change the next decision. Record:

- expected versus observed result;
- which assumption or mechanism held or failed;
- what evidence changed the judgment;
- what should continue, shrink, pivot, or stop;
- which rule, resource allocation, artifact, or next action changes.

Do not write a chronology that leaves the operating rule unchanged.

## Resource-Decision-Execution Cross-Check

Run this separately from the six stages:

| Check | Requirement |
| --- | --- |
| Resources | Inventory only people, time, money, evidence, distribution, assets, tools, and permissions that change the route. For a gap choose acquire, borrow, substitute, reduce scope, delay, or stop. |
| Decision | State the actual choice, who owns it, what is authorized now, and what evidence would reverse it. |
| Execution | Name the next artifact/action, owner or acquisition, failure signal, review input, and next branch. |

## Completion Test

Before calling the work decision-ready, ask:

1. Is the real decision visible?
2. Did the research and decomposition reveal a decisive crux rather than a complete-looking category list?
3. Does the recommendation reflect actual resources and make a choice?
4. Can the next bounded action start without inventing authority or facts?
5. Will the retrospective change a future decision?
6. Is any polish making weak work look finished?

If the sixth answer is yes, state the gap instead of presenting completion.
